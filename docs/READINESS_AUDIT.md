# MedCipher independent readiness audit

Audit date: 20 November 2026. Scope: source, original PRODUCT_REQUIREMENTS.md and master inventory, hosted Supabase, GitHub/CI and Vercel. This is an engineering assessment, not an independent third-party certification or medical validation. Tests use synthetic records exclusively. **Full master acceptance is not achieved.**

## Evidence and limits

- **U**: 55 passing Vitest assertions, including 33 domain cases, validation, auth provider failures, cryptographic tampering/scope and sorting 10,000 synthetic queue entries.
- **I**: 33 passing live hosted integration assertions in scripts/integration-check.mjs.
- **R**: tests/audit-rls.sql passed against hosted PostgreSQL: eight roles, two tenants, foreign reads/mutations, registration/configuration permission matrix, direct role/audit write denial, expired/revoked/scoped tokens, token rate limit, disposition integrity. Fixtures are transactionally rolled back. These are SQL/JWT-role tests, not eight separate browser sessions.
- **B**: seven local browser scenarios passed in 50.6 seconds; the corrected hosted preview passed eight scenarios in 56.1 seconds and production passed all eight in 53.8 seconds, using live synthetic Auth and database. Includes registration through discharge, patient emergency/intake/language, encrypted offline capture with simulated HTTP 503 and recovery, responsive/axe dashboard, anonymous emergency guidance, hospital selection denial, refresh/logout failure reporting.
- **L**: hosted synthetic smoke load in AUDIT_LOAD_RESULTS.json: 20 registrations at concurrency five; ten simultaneous retries produce ten acknowledgements and exactly one encounter; ten emergency requests produce one alert; five resource contenders produce one winner. Forty measured registration/retry/emergency calls: p50 110 ms, p95/max 180 ms on this run. This is not a sustained capacity benchmark or Vercel HTTP latency test.
- **RT**: scripts/realtime-check.mjs verifies hosted event delivery and explicit disconnect/resubscription.
- **S**: source and migration inspection, not executable acceptance. A feature with only S evidence remains incompletely verified.
- Deployment evidence is recorded in DEPLOYMENT_STATUS.md. This report's matrix describes the audited source; deployment is only established by that separate record.
- All 28 public tables have RLS; six migrations are applied. No destructive reset, disabled failing test or clinical enablement occurred.
- Actual provider outage, backup restore, region loss, long network partition, sustained high load, all-route screen reader and real receiving-hospital delivery were **not** tested.

## Defects corrected during this audit

1. Reproduced concurrent registration retry failure: baseline had four unique-key errors in ten calls despite one saved encounter. Transaction advisory locking now returns ten successful acknowledgements and one encounter.
2. Provider failures in logout/recovery previously could produce false success. Strict bounded auth requests and explicit 503 responses now cover these paths; local sign-out avoids invalidating other synthetic demonstration sessions.
3. Offline payloads were plaintext. New drafts encrypt with AES-GCM and bind operation/user/hospital. Sync is serialized, checks a server encounter acknowledgement, and retains failed drafts. Browser test verifies ciphertext and outage/retry.
4. Patient warning “unknown” could become false. It now persists as null and no longer forces a normal/abnormal choice.
5. Older refresh responses could overwrite newer workspace data. A sequence guard discards superseded responses. A deliberately out-of-order browser test now passes. Preview testing also found a command-completion race: saves now wait for any superseding snapshot before enabling the next versioned action.
6. Snapshot escalation errors were ignored; failures now fail the snapshot with 503 rather than claiming refreshed tasks.
7. An arbitrary Admission/Discharge note could create structured disposition records without the state flow. Database now requires the documented transition, tested by R.
8. Token request lock order differed from staff mutations. Both now lock encounter before capability; token validity is rechecked after lock. Rate buckets are created only for valid tokens and aged buckets cleaned.
9. Latest-500 encounter selection could silently omit an old active case. Active encounters are paged separately; closed history remains capped at 500 and coverage is visible. Patients are fetched by encounter IDs. A 10k ceiling fails rather than silently dropping the queue. Concurrent page movement remains a scaling limitation.
10. Ineligible resource/investigation actions were shown to roles denied by the server. UI options now reflect those permissions; database remains authoritative.
11. Patient HTTP failures now use errors/status codes; QR generation/copy rejection produces actionable messages instead of an unhandled promise.

## Security and encryption assessment

Transport uses HTTPS to Vercel and Supabase; browser draft encryption and tamper rejection are tested. Provider disk/backup encryption, key rotation, restore capability and residency contracts were not independently verified. A nonextractable IndexedDB key is not a secure enclave and does not protect against active same-origin scripts or an unlocked browser profile. No real PHI is permitted.

Supabase advisors still warn about deliberate SECURITY DEFINER entrypoints: one anonymous capability RPC and four authenticated commands. Their access checks were tested; warnings are not suppressed. See [anonymous definer guidance](https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable) and [authenticated definer guidance](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable). [Leaked-password protection](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection) is disabled and remains an account-side blocker.

## Clinical safety and required external review

Emergency warning evidence takes precedence over the demonstration score. Missing data remains unknown; no automatic GREEN from absent warnings. Category order is preserved; elapsed wait creates reassessment work rather than silently changing clinical urgency. Clinician recommendations/decisions are retained with authenticated account attribution. Technical failure instructions direct people to staff; the software cannot guarantee manual care delivery.

Qualified clinicians must review warning signs, unassessed queue handling, category semantics, numeric model, reassessment intervals, deterioration response, specialty routing, override permissions, admission/discharge/transfer criteria, resource shortage response, follow-up, translated wording, accessibility, downtime SOP and audit accountability. A medical-device/regulatory determination, privacy impact assessment, consent/retention rules and clinical evaluation are not supplied by software tests.

## Unfinished acceptance

Every original requirement remains inventoried in MASTER_REQUIREMENTS_CHECKLIST.md; unchecked requirements are not waived. The audit does not establish that every advertised button/form, role combination, report or failure mode has been end-to-end accepted. Only the evidence above is claimed. Missing modules must be implemented and independently accepted before expanding beyond a synthetic demonstration. No single “production-ready” badge is appropriate.

Performance advisor follow-up: 55 unindexed foreign-key and five unused-index informational findings remain. They require workload-specific query-plan review before production sizing; the bounded smoke-load result does not dismiss them. No indexes were dropped based on low demo usage.

Performance advisor remediation references: [foreign-key indexing](https://supabase.com/docs/guides/database/database-linter?lint=0001_unindexed_foreign_keys), [unused index review](https://supabase.com/docs/guides/database/database-linter?lint=0005_unused_index).
